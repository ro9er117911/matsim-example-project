MATSim（多代理交通模擬）框架是一個基於活動（Activity-based）、可擴展且開源（Open-source）的多代理模擬平台，主要採用共同演化演算法（Co-Evolutionary Algorithm）來優化個體代理人的日常活動排程，以尋求交通系統的**使用者平衡（User Equilibrium）**狀態。

### MATSim 交通模擬框架核心要素摘要

| 核心領域 | 概念與機制 | 實作細節與參數 | 文獻出處 |
| :--- | :--- | :--- | :--- |
| **I. 核心架構與目標** | | | |
| **基礎模型** | 基於活動（Activity-based）和多代理（Multi-agent）的模擬框架，專為大規模場景設計。 | 核心邏輯使用 Java 實現，強調計算效率和並行化。 | |
| **運作循環** | MATSim 循環（Loop）是迭代過程，包含四個主要階段：初始需求 $\rightarrow$ 移動模擬 (Mobsim) $\rightarrow$ 評分 (Scoring) $\rightarrow$ 重新規劃 (Replanning) $\rightarrow$ 分析 (Analyses)。 | 運行週期由 `controller` 模組中的 `lastIteration` 參數設定迭代次數。 | |
| **II. 迭代機制與收斂** | | | |
| **計畫（Plan）** | 每個代理人維持一個有限的日常活動排程集合（Memory），其中只有一個計畫會被選中執行（`selected="yes"`）。 | 記憶體最大容量（Plan Memory Size）可配置，例如預設為 5。 | |
| **評分機制** | 根據 Mobsim 執行結果計算計畫的效用/分數（Score），通常採用 **Charypar-Nagel 效用函數**。 | 效用包含活動效用 (`Sact,q`) 和交通段不效用 (`Strav,mode(q)`) 的總和，涉及模式常數、旅行時間、距離和貨幣參數（`βm`）。 | |
| **重新規劃** | 策略模組負責修改或選擇計畫。創新策略（Innovation）創建新 Plan（如 `ReRoute`、`SubtourModeChoice`），選擇策略（Selectors）則從現有 Plan 中挑選。 | 模式創新策略包括 `ChangeLegMode`、`ChangeSingleLegMode` 和 `SubtourModeChoice`。 | |
| **強制收斂** | **MSA (Method of Successive Averages)** 用於確保計畫分數收斂到其期望值，尤其適用於迭代後期。 | 啟用參數：`<param name="fractionOfIterationsToStartScoreMSA" value="..." />`，將固定混合參數 $\alpha$ 替換為變數 $1/m$ ($m$ 為執行次數)。 | |
| **III. 移動模擬 (Mobsim) 與數據** | | | |
| **Mobsim 模型** | 預設為 **QSim** (Queue-based Simulation)，基於佇列模型，透過時間步長（Time-step based）模擬交通流和擁堵，計算效率高但犧牲了精細的跟車行為。 | 交通流動基於兩個關鍵連結屬性：**儲存容量（Storage Capacity）**和**流量容量（Flow Capacity）**。 | |
| **數據單位** | 距離單位通常為**米（meters）**，因為 MATSim 建議使用笛卡爾坐標系（如 UTM）。時間單位在內部預設為**秒（seconds）**，但計分參數使用**小時（hour）**。 | 座標系統設定在 `global` 模組中，建議使用 EPSG 代碼指定。 | |
| **核心輸出** | 模擬結果以事件流（Events）形式生成，用於分析各類聚合數據。 | 標準輸出包括以 CSV 格式儲存的摘要統計文件，例如 `scorestats.txt` 和 `traveldistancestats.txt` (Tab 分隔)。 | |

| **動態運輸 (DVRP)** | Dynamic Vehicle Routing Problem 擴展，允許駕駛員/代理人執行動態行為，持續接收來自調度員的指令。 | 採用 **DynAgent** 類別實現動態行為，而非預先計算的計畫。DVRP 模擬通常作為**單次迭代模擬**運行。 | |
| **公共運輸 (PT)** | 支援詳細的排程公共運輸模擬，車輛沿固定路線運行，並監控容量和速度。 | 需額外輸入 `transitSchedule.xml`（運營時刻表）和 `transitVehicles.xml`（車輛類型和容量）。路由演算法包括高效的 **SwissRailRaptor**。 | |

先別急著說自己笨。這份內容其實是在講一個把「城市裡每個人的一天」用電腦反覆模擬、評分、再改計畫，直到大家都覺得「再怎麼改也不會更好」為止的系統。你可以把它想成：每天上班的人都在用昨天的經驗調整今天的通勤，整座城市就這樣一輪一輪學習，最後形成穩定的交通格局。[1][2]

一、整體在做什麼（一句話版）

流程是「模擬 → 打分（效用/分數） → 改計畫 → 再模擬」，重複好多次，直到接近「使用者均衡」：任何人單獨改自己的通勤，都不會比現在更好。[2][3][4]

二、系統結構（從輸入到收斂）

初始需求 Initial Demand：先為每個人建立一天的活動鏈（例如：家→工作→購物→休閒→家），每個人記憶體裡可以存多個計畫。[5]  

Mobsim（移動模擬）：把大家選的計畫丟進路網跑一遍，會產生擁塞、排隊、等車等真實效果。預設的模擬器叫 QSim。[6]  

Scoring（評分）：根據「這一輪實際發生」來算每個人的計畫分數（經濟學裡的效用），常用 Charypar–Nagel 函數。分數高的計畫比較可能被保留。[7]  

Replanning（重新規劃）：複製或修改計畫（改出發時間、路線、模式、目的地），並用隨機效用選擇模型挑下一輪要執行的計畫。ChangeExpBeta 讓高分計畫機率高、但保留嘗試的隨機性；也會用到 ReRoute 與 SubtourModeChoice 等策略。[8][9]  

反覆迭代直到收斂：大家互相影響、一起學，最後趨近使用者均衡。[2][10][3]

三、一天的計畫長什麼樣（名詞超白話）

Plan（計畫）：一個人一整天「活動與交通段」交替的清單，例如 家(h) → 走路 → 轉乘互動 → 搭捷運 → 走路 → 工作(w) → … → 回家。[11][12]  

Trip（行程）：兩個「真正的活動」之間的整段移動（裡面可含多個交通段與轉乘互動）。[13][12]  

Leg（交通段）：單一模式的一段移動（只走路、只搭捷運、或只開車），是 Trip 的基本單元。[14]  

四、評分模型（核心數學，照原意簡化講）

總計畫效用＝所有活動效用＋所有旅行效用（旅行通常是負分）。  

$$
S_{plan} \;=\; \sum_{q=0}^{N-1} S_{act,q} \;+\; \sum_{q=0}^{N-1} S_{trav,mode(q)}
$$

重點：活動帶來正效用；旅行通常扣分。[15][16]

活動效用（做事的快樂/價值）主要由「做了多久、和理想時長差多少、早到晚到是否被罰」構成：  

$$
S_{dur,q} \approx \beta_{perf}\, t_{typ,q}\,\ln\!\Big(\frac{t_{dur,q}}{t_{typ,q}}\Big) \;+\; \beta_{perf}\, t_{typ,q}\,\frac{1}{prio_q}
$$

其中 $\beta_{perf}$（又寫作 $\beta_{dur}$）常設約 6 utils/小時；若晚到，會有遲到懲罰（例如 $\beta_{late.ar}=-18$ utils/小時；早出發也有類似懲罰）。[17]

遲到怎麼扣分（例）：原本 09:00 前要到，若 09:15 才到，晚 0.25 小時，扣 $0.25\times(-18.0)=-4.5$ 分。很痛，所以大家會調整出發時間避免遲到。[18]

旅行負效用（移動本身的痛苦/花費）長這樣：  

$$
S_{trav,q} \;=\; C_{mode(q)} \;+\; \beta_{trav,mode(q)}\, t_{trav,q} \;+\; \beta_m\, \Delta m_q \;+\; \big(\beta_{dist,mode(q)} + \beta_m\, \gamma_{dist,mode(q)}\big)\, d_{trav,q} \;+\; \beta_{transfer}\, x_{transfer,q}
$$

直譯：一段移動的分數＝模式常數＋「這個模式每小時的直接好惡」×時間＋「金錢邊際效用」×付了/省了多少錢＋「距離本身帶來的不舒服」與「按距離收費」的合計＋「是否轉乘的扣分」。[19]

金錢邊際效用與收費例子：若 $\beta_m$ 乘上「花了 5 元」就等於扣 5 分，代表繳費很傷分；因此走收費道路（多花 5）會讓旅行效用多扣 5。[20]

轉乘不爽度：公共運輸若需要換線，每次可扣 1 分（舉例設定 $\beta_{transfer}=-1.0$）。[21]

距離兩種扣分法：  

非貨幣性距離不效用 $\beta_{dist,mode(q)}$（例如走路會累）；  

貨幣距離費率 $\gamma_{dist,mode(q)}$ 乘 $\beta_m$（例如開車每公里油錢）。兩者相加後再乘距離。[22][23]

時間到底怎麼扣？一部分是「旅行本身的直接喜惡」$\beta_{trav,mode}$，另一部分是「你為了旅行而少做活動」的機會成本（活動的 $\beta_{perf}$ 代表做正事的價值）。很多研究把「討厭在路上浪費時間」的感覺，放在活動的機會成本裡；因此車上的 $\beta_{trav,car}$ 常接近 0 或略為負。[24][25]

一些參數範例（直接來自設定檔）  

Car：$\beta_{trav,car}=-6$ utils/h；每米貨幣距離費率 monetaryDistanceRate = -0.0002。  

PT：$\beta_{trav,pt}=-7$ utils/h；距離相關項設為 0（示例）。  

Walk：$\beta_{trav,walk}=-12$ utils/h（走路久會更累）。這些都會與上面的總式一起計分。[26][19]

一個超直白的整日分數範例：  

$$
80 \;=\; 100 \;+\; (-20)
$$

讀作：「活動加起來值 100 分，但交通扣了 20 分，整天拿到 80 分」。[27][28][29]

五、為什麼會「越跑越像真的」

微觀互相影響：某人選擇開車會讓某路更塞，害別人晚到、被扣分；下輪別人就會改路或改搭捷運，如此迭代，跟真實世界很像。[30]  

跟傳統「四步法」不同：不只看平均，能看每個人的決策與經驗。[31][1]  

目標是「使用者均衡」：當大家怎麼改都不會再更好，就算收斂。[2][3]

六、學習與收斂是怎麼發生的

代理人不是死盯最高分那個計畫，而是用 ChangeExpBeta 這種「分數愈高、機率愈大，但仍保留探索」的選擇機制；同時透過 ReRoute/ SubtourModeChoice 引入改路徑/改模式的創新。這樣避免卡在壞的局部解。[9][8]  

MSA（逐次平均法）會在後期讓分數更穩、更收斂到期望值。[32]  

真實的迭代例子：一開始執行的是自駕；發現捷運更好後，幾輪內改成捷運，再微調成「捷運＋走路」拿到更高分。[33]  

群體層次的均衡直覺：例如最後大約 30% 開車、70% 搭捷運，誰想單獨改都不會更好。[3][4]

七、輸入長什麼樣、輸出要看什麼

輸入的樣子：每個人的 population.xml 裡列出一天的活動與交通模式（可見走路、車、捷運與轉乘）。[34]  

模擬過程的事件流：output_events.xml.gz 會記錄每個人每件小事（出發、到達、等車、上車…），所有統計都是從事件累計出來。[35][36]  

重要統計與圖表：  

scorestats.csv/.png：看每輪的平均/最佳/最差/已執行分數，曲線穩了就代表快收斂。[37][38]  

modestats.csv/.png：看各模式（車/捷運/走路）的份額變化。[39]  

pkm_modestats、ph_modestats：看各模式的客公里/客小時，衡量載運量與使用強度。[40]  

traveldistancestats（csv/png）：看行程與單段的距離分布。[41]  

stopwatch.csv：看每輪各階段耗時，找瓶頸（Mobsim 通常最久）。[42][37]

八、怎麼讀懂 pkm/ph 這些數字（舉例）

一輪模擬匯總的例子：自駕 14 人小時、650 人公里（約 46 km/h），捷運 31 人小時、920 人公里（含等車約 30 km/h），走路 84 人小時、389 人公里（約 4.6 km/h）。這些數字能對照到分模式的 ph、pkm 圖表與欄位說明。[43][44][45]

九、兩種收斂情景（為何有時候「太早卡住」）

理想收斂（A）：大家有足夠機會探索不同模式與路線，最後收斂得漂亮。[46]  

早期收斂（B）：探索不夠或策略不對，太早卡在某種選擇，導致分數其實還能更好卻碰不到。提升「模式覆蓋率」與使用 SubtourModeChoice 等策略可改善。[47][48][9]

十、把模型當成生活化的直覺

你在路上多花 1 小時，等於少做 1 小時有價值的活動；若活動的邊際效用約 6 分/小時，那旅行的「機會成本」大概就扣了 6 分。這就是為什麼模型會自動幫你「討厭浪費在路上」。[25][17][24]  

付錢會心痛：付費道路多 5 元就再扣 5 分；轉一次車再扣 1 分；晚到 15 分鐘再扣 4.5 分。這些小懲罰累積起來，就把日常的感受數量化了。[20][21][18]

如果你只想抓關鍵：記住四件事——(1) 每個人有一堆可選的一天行程（Plan）；(2) 模擬一輪拿到真實延遲與等車，再用效用函數打分；(3) 透過隨機效用的選擇與創新策略改計畫；(4) 反覆到大家都改不動更好，這就是使用者均衡。[11][6][19][9][2]
